# 0.6.1 리빌드와 반복 요청 최적화 — 2026-10-02

0.6.0의 현장용 변경을 유지하면서 반복 요청 검색과 Cursor 상태 응답을 줄였다. 영상 계산 코드·모델·프롬프트·프레임 수는 바꾸지 않았다. 기존 일반 해변 검증과 현장 품질 실패 기록을 그대로 유지한다. **SORA2급 현장 사실감·실제 모델 재학습·LG 그램 실행은 달성하거나 검증하지 못했다.**

## 이번 변경

- 같은 요청은 `cache/request-index`에서 이전 작업을 찾는다. 실제 작업의 요청 해시·상태와 완료 영상의 SHA256을 다시 확인하며, 잘못된 검색 기록·없는 작업·변경된 파일이면 재사용하지 않는다. 검색 기록이 없어도 기존 작업을 찾을 수 있다. 일반 제작의 자원과 품질 확인은 검색보다 먼저 수행한다.
- 완료 응답에서는 이미 끝난 단계 수·진행량과 반복되는 경로·밝기 검사 설명을 덜어냈다. 실제 영상·출처·검토 표시·현장 초안 경고·재학습 및 사실감 미검증 표시는 유지한다. 상세 계산 기록은 결과의 `details_path`가 가리키는 D의 `result.json`에 남는다. 진행 중과 실패 응답의 메모리·진행·오류·로그 경로는 유지한다.
- JSON 응답의 불필요한 공백을 줄였다. 기존 MCP 도구 6개와 초기화 방식은 유지한다. 실제 연결 검사는 현재 서버 버전을 읽어 대조하도록 수정했다.

## 바꾼 부분

- 준비된 INT8 가중치는 출처·원본 해시·Torch 버전·파일 SHA256을 확인한다. 크기·시간·파일 식별 값이 같으면 확인 기록을 재사용하며 변경 시 다시 해시를 계산한다. 모델 준비를 확인하려고 매 장면 Torch 프로세스를 띄우지 않는다. 관측한 준비 단계는 0.4.0 약 10초에서 0.5.0 최초 해시 확인 1.391초·재사용 0.016초로 줄었다.
- 텍스트 임베딩과 시작 이미지 잠재값을 별도로 캐시한다. 입력과 모델·코드가 다른 경우 재사용하지 않으며 같은 크기의 손상도 SHA256으로 걸러낸다. seed 42·43에서 텍스트 텐서 3개가 정확히 같은 것을 실제 계산으로 확인했다. 이미지 인코딩의 확률적 표본은 seed까지 구분한다.
- 단계별로 필요한 모델 클래스만 가져오도록 정리했다. 이 변경만의 시간 개선을 별도로 측정하지 않았으므로 독립 속도 효과를 주장하지 않는다.
- 한 장면은 원래 인코딩된 클립을 그대로 저장한다. 재압축을 피하며 테스트에서 파일 바이트 보존을 확인했다. 여러 장면의 컷 연결 경로는 기존 프레임 조합을 유지한다. 인코더·디코더의 CPU 스레드는 각각 2개로 제한했다.
- 설치 재실행은 다른 MCP 서버와 사용자 자원 설정을 보존한다. 불완전한 라이브러리 명세는 실행 준비 오류로 보고한다.

## 리빌드와 검증

캐시 무효화·손상·취소·변환 가중치 출처·다른 서버 보존·단일 클립 바이트 보존을 포함한 **81개 검증이 2.408초에 통과**했다. `audits/unit-tests-rebuild.txt`. 새 영상은 49프레임 전체 해독과 출력 검사를 통과했고 프레임 비교 이미지에서 해변·수면 변화를 확인했다. 이는 한 장면의 시각 검토이며 복잡한 동작의 품질 보증이 아니다.

리빌드 도구는 Python 소스를 구문 검사하고 앱 소스·라이선스 고지·검증 샘플을 ZIP으로 묶는다. 고정 ZIP 시간과 파일 순서를 사용하며 파일별 SHA256·CRC·검증 영상 해시를 검사한다. 실행 라이브러리 바이너리나 모델 가중치는 묶지 않는다. D의 `releases\LATEST.json`에 최신 ZIP과 전체 SHA256을 기록한다. 공식 고정 엔진을 소스에서 다시 컴파일했다고 표시하지 않는다.

CPU 실행 환경과 INT8 모델은 기존 검증된 고정 버전을 재사용한다. 모델·캐시·임시 파일·결과의 D 전용 규칙과 시작 RAM 3GiB·실행 여유 1GiB·추론 상주 5GiB 보호 기준은 유지한다. 실측 사용량을 고려한 여유 RAM 5~6GiB 권장도 유지한다.
