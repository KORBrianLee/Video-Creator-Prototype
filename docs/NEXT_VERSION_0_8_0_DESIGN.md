# 0.8.0 설계 — 두 개발 분기의 강점 통합

## 설계 근거(우선순위 순)

1. **이 개발 PC(16GB RAM, Intel Iris Xe 내장 GPU)에서 안정적으로, 효율적으로 동작한다.** 다른 컴퓨터의 결과나 일반 정책보다 이 PC의 실측을 우선한다.
2. **좋은 품질.** 장비와 작업자가 보이고, 형태가 유지되고, 화면이 무너지지 않는다. 고정 판정표로 확인한다.
3. **길이는 최대 15초가 목표다.** 이 PC에서 성능 한계가 실측으로 분명하면 **8초로 제한한다.** 길이를 위해 품질이나 안정성을 희생하지 않는다.

Cursor 대본으로 장비와 작업자가 함께 움직이는 연속 영상을 만든다. 외장 GPU가 있는 다른 컴퓨터는 같은 구조로 자동 적응한다. 이 문서는 설계이며 아직 구현·검증된 것이 아니다.

## 비교한 두 분기

- **A: 보호·검증 분기(0.7.10 소스 후보, 활성 0.7.9).** 다른 컴퓨터에서 개발했다. 실행 폴더의 `continuation/` 아래에 원본과 인수인계 문서가 있다.
- **B: GPU·적응 분기(이 저장소의 0.7.3 이후 작업).** 이 PC(그램급 Iris Xe)에서 개발했다.

## 최우선 원칙: RAM 낭비 최소화와 적응형 동작

이 PC는 RAM 16GB에 평소 여유가 2~8GB로 계속 바뀌고, GPU도 그 RAM을 나눠 쓴다. 그래서 RAM을 아끼는 것이 곧 속도와 안정성이다.

**고정량을 확보하지 않는다(탄력형 메모리, 적용됨).** 지금 쓸 수 있는 만큼 쓰고, 여유가 생기면 더 쓰고, 부족하면 느리게 진행한다.

- 물리 RAM이 적어도 시작한다. 읽기 전용으로 매핑한 가중치는 Windows가 버렸다가 다시 읽으므로, 부족하면 느려질 뿐 실패하지 않는다.
- RAM이 빠듯하면 저메모리 모드로 계속 실행한다. 10초마다 그 단계의 작업 집합을 비워서 매핑 페이지부터 내린다.
- 작업을 멈추는 기준은 commit(RAM + 페이지 파일 중 Windows가 아직 약속할 수 있는 양)이 바닥날 때뿐이다. 하한은 commit 한도의 4%, 최소 0.75GiB다. 실제로 모든 프로그램의 메모리 할당이 실패하기 직전이 그 시점이다. 측정 당시 이 PC는 여유 RAM이 2.5GiB뿐이었지만 commit 여유는 14.8GiB였다.
- 학습된 단계별 필요량은 시작을 막는 기준이 아니라 commit 확인과 진행 예측에만 쓴다.
- 고정 작업 메모리 상한은 사용자가 숫자로 지정했을 때만 적용한다.

모든 단계는 다음 순서로 동작한다.

1. **시작 전 측정:** 지금 여유 RAM, GPU 종류와 공유 여부, 학습된 단계별 필요량을 읽는다.
2. **설정 선택:** 그 값으로 attention 조각 크기, 가중치 상주/스트리밍, 스레드 수, 시작 허용 여부를 정한다.
3. **실행 중 감시:** RAM과 commit을 감시하고, 위험하면 그 단계만 멈춘다.
4. **끝난 뒤 기록:** 실제 최대 사용량을 기록해 다음 실행의 기준으로 쓴다.

확인된 RAM 낭비 원인과 처리:

| 낭비 원인 | 크기(실측·계산) | 처리 | 상태 |
|---|---|---|---|
| Safetensors와 Torch의 쓰기 복사 매핑 중복 | 파일 크기만큼 commit이 한 번 더 잡힘(Neo 3.1GB → 6.3GB) | 읽기 전용 단일 매핑 로더(`readonly_weights`): Neo, LTX(diffusers), T5(transformers) | 적용, 실측 중 |
| 수학 라이브러리 스레드별 버퍼 | 스레드 수에 비례 | OMP·MKL·OpenBLAS·NumExpr 스레드를 같은 값으로 제한 | 적용 |
| 모델 전체를 FP32로 변환 | LTX VAE 2.3GB → 4.6GB, Neo 3.1GB → 6.3GB | BF16을 유지하고, 호출할 때 해당 행렬·컨볼루션만 GPU에서 FP32로 펼침 | 적용 |
| attention 점수 행렬 전체 생성 | T=6000에서 3.3GiB | 여유 RAM에 맞춘 질의 분할(메모리가 길이에 선형) | 적용 |
| 외장 GPU에서 매번 가중치 전송 | 전송 시간 | VRAM에 들어가면 상주, 아니면 스트리밍 | 적용 |
| Neo 생성자의 float64 위치 배열 | 일시적으로 0.45GB + 0.23GB | 버려지는 배열을 만들지 않는 생성 경로(0.7.10 후보) | 계획 |
| 단계 간 큰 인코더 재로딩 | 단계마다 수 GB 읽기 | 조건 캐시(문장·첫 프레임 결과 재사용), 단계별 별도 프로세스로 끝나면 즉시 반환 | 기존 |
| 전체 작업 메모리 상한 부재 | 하위 프로세스 합산 미통제 | Windows Job으로 commit 5GiB 제한(0.7.10) | 계획 |

모든 단계 기록에 Windows가 실제로 제한하는 값인 commit 최대치(`peak_commit_bytes`)를 남긴다. 요약(`digest`)에는 `[초, 비공개 상주 GiB, commit GiB]`로 나온다.

## 채택하지 않는 것

- 보호 상한을 몰래 올리는 변경. B의 XPU 단계는 작업 집합 5.6~6.2GiB, GPU 할당 0.43~0.57GiB로 A의 상한(작업 5GiB, 명시 GPU 64MiB)을 넘었다.
- 실패한 GPU 단계를 자동으로 CPU에서 다시 실행하는 것. 사용자에게 보고하고, 대체 실행은 명시적으로 요청할 때만 한다.
- 독립 클립 연결, 루프, FPS 변경, 슬로모션으로 길이를 늘리는 것.

## GPU 메모리 상한: 이 PC 기준으로 결정

A의 명시 GPU 버퍼 64MiB는 OpenCL Linear 한 행렬을 기준으로 정한 값이라, 활성값 전체를 GPU에 두는 XPU 경로에는 맞지 않는다. 설계 근거 1에 따라 이 PC에서 빠르고 안정적인 XPU 경로를 기본으로 하고, 상한은 고정값 대신 이 컴퓨터의 공유 메모리에서 계산한다.

- **XPU 기본 경로(Intel GPU):** GPU 할당 상한은 `min(1GiB, 전체 RAM의 6%)`로 한다. 16GB PC에서는 약 0.96GiB다. 실측 피크는 0.43~0.57GiB였다. OS Job commit은 5GiB를 그대로 지킨다. 실측에서 매핑을 뺀 비공개 사용량은 2.7~2.9GiB였으므로, 읽기 전용 로더를 쓰면 commit 5GiB 안에 들어갈 가능성이 크다. 1차수에서 이것을 실측으로 확인한다.
- **OpenCL 경로(XPU가 안 되는 Intel·AMD):** 64MiB 정책을 그대로 지킨다.
- 상한을 넘으면 그 작업만 멈추고 보고한다. 상한을 자동으로 올리지 않는다.

## 길이 정책: 8초 기본, 15초는 실측으로 열기

- **기본 최대 8초.** Neo로 이 PC에서 안정적으로 만들 수 있는 길이다(XPU 8초 실측 512초). 단, 8초 품질도 판정표로 다시 확인한다. 기존 8초 결과에는 후반 어두워짐이 있었다.
- **15초는 LTX 2B(이 PC의 XPU)로만 연다.** 아래 조건을 모두 통과해야 정식 길이로 허용한다.
  - 2초 → 8초 → 15초 순으로 판정표를 통과한다.
  - 15초 1회 생성 시간이 이 PC에서 실용적인 범위다. 기준선은 Neo 8초(약 9분)이고, 15초는 그 2배(약 20분) 안이어야 한다.
  - Job commit 5GiB와 GPU 상한을 지킨다.
- 하나라도 실패하면 **8초 제한을 확정**하고, 실패 근거(시간·메모리·붕괴 시점)를 기록한다. 이 경우 15초는 진단용으로만 남긴다.

## 저장 위치

A는 C 드라이브 여유 200GiB를 요구한다. 이 PC의 C는 느린 USB 시스템 드라이브이고 여유는 약 40GiB라 그 조건을 통과하지 못한다. 0.8.0은 컴퓨터마다 실행 폴더를 고르는 기존 방식(`runtime-dir.txt`)을 유지한다. 여유 공간 기준은 드라이브가 아니라 선택한 실행 폴더 기준으로 판단한다. 기준을 낮추려면 사용자 승인이 필요하다.

## Cursor 에이전트와 로컬 프로그램의 역할 분담(적용됨)

토큰을 가장 많이 쓴 것은 실행 중인 작업을 에이전트가 반복 조회한 일과, 긴 상태 JSON·로그를 읽은 일이었다. 화면 붕괴도 이미지로 직접 확인해야만 알 수 있었다. 이를 다음처럼 나눈다.

| Cursor 에이전트 | 로컬 프로그램 |
|---|---|
| 목표·병목 선택, 코드 수정, 계획(JSON) 작성 | 생성 실행, 대기, 단계별 시간·메모리 측정 |
| 요약 한 번 읽고 판단, 다음 계획 결정 | 화면 신호 계산: 어두워짐, 색 붕괴, 검은 프레임, 정지 의심 |
| 경고가 있을 때만 대표 이미지 1장 확인 | 시도 상한(계획당 6회), 같은 실패 2회 시 중단, 붕괴 시 더 긴 길이 생략 |
| 내용 품질·사용자 수용 판정 | 4KiB 이하 요약 파일 작성 |

- `video.cmd digest <job>` / MCP `video_digest`: 끝난 작업 하나의 2KiB 이하 요약이다(실측 약 700바이트).
- `video.cmd plan <file>`: 계획을 로컬에서 끝까지 실행한다. 에이전트는 이를 백그라운드로 시작한 뒤 턴을 끝낸다. Cursor 완료 알림이 오면 요약만 읽는다.
- 규칙 `.cursor/rules/agent-local-split.mdc`가 이 방식을 강제한다. 셸 반복 조회, 긴 대기, 전체 로그 읽기를 금지한다.
- 화면 신호는 이 PC의 실제 실패로 기준을 정했다. Neo 15초(어두워짐 후 파란 잡음), Neo 8초(중간에 93에서 49로 어두워짐)는 경고가 나오고, Neo 2초의 완만한 변화(105에서 90)는 경고가 나오지 않는다. 신호는 경고일 뿐이며 품질 통과가 아니다.

## 차수 계획(순서만 고정, 일정은 고정하지 않음)

1. **15초 가능성부터 판정한다(이 PC).** 이미 설치된 LTX 2B로 2초 → 8초 → 15초를 각각 1회 생성해 시간·메모리·화면 붕괴를 잰다. 길이 정책(8초 또는 15초)이 여기서 정해지고, 이후 차수의 범위가 달라지므로 가장 먼저 한다. 큰 다운로드는 없다.
2. **보호 통합.** A의 Job 보호, 읽기 전용 로더, 스레드 상한, 선택 RAM 대기를 이 저장소에 들인다. XPU·LTX 단계도 Job 안에서 실행한다. 통과 조건은 모든 단계의 OS Job commit 실측이 5GiB 이하이고 Job이 비는 것이다.
3. **평가 도구.** 고정 장면 3개와 판정표를 구현하고, 첫 화면 대상 확인을 넣는다. 자동 검사와 사람 검토 결과를 분리해 기록한다.
4. **품질 기준선.** 장비 1대, 작업자 1명, 행동 1개의 장면을 정해진 길이로 만든다(1차수 결과에 따라 8초 또는 15초). XPU와 OpenCL을 같은 장면으로 비교해 시간·메모리·판정을 기록한다.
5. **안정화.** 성공률, 처리 시간, 메모리, 품질 중 가장 큰 격차 하나를 고른다. NVIDIA용 SkyReels 경로는 해당 PC가 생기면 같은 판정표로 검증한다.

## 0.8.0 완료 조건

- 1차수에서 길이 정책(8초 또는 15초)이 실측 근거와 함께 확정된다.
- 2~3차수 통과.
- 4차수: 정한 길이의 영상이 이 PC에서 판정표를 통과한다. 화면 붕괴가 없고 장비와 작업자가 보여야 한다. 통과하지 못하면 원인과 다음 목표를 기록한다.
- 모든 수치는 이 PC 실측으로 기록하고, 다른 컴퓨터의 수치와 섞지 않는다.
